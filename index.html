Case lifecycle

New → Triage → In progress ⇄ Awaiting citizen → Resolved → Closed. Triage can go straight to Resolved (for example, a duplicate or a non-council repair). A resolved case can be reopened by its owner or a team leader; only a team leader can close it. Resolving needs a resolution note. The SLA clock pauses while the case is awaiting the citizen.

SLA targets

These targets are illustrative local policy and run on calendar time. A real service sets its own, usually in working days against a business-hours calendar. The pause while awaiting the citizen is an internal SLA convention; it would not stop a statutory clock.

Context: in England, Awaab's Law has applied to social landlords since 27 October 2025. It sets legal timescales for emergency hazards (investigated and made safe within 24 hours) and for significant damp and mould. That is why this demo won't let damp and mould be logged as Routine. The actual rules would come from the council's repairs policy and legal advice, not from me.

    4 · Dataverse and Dynamics 365 design

    How I'd model it on Dataverse and Customer Service

    Concept design · details to confirm with the solution architect

    The demo above runs in the browser. In the real programme, the same rules would sit on Dataverse with a model-driven app (forms, views, the timeline and a business process flow to guide the stages), using standard Customer Service tables where they fit instead of building custom ones. Treat the detail as a starting point for a conversation with the architect.

    Table model

    TableTypePurpose and key columns
    Case (incident)StandardOne repair request. Title, customer (the standard Customer lookup, a Contact here), category and priority (choices), status and status reason, owner (user or team), property (lookup), legacy reference, SLA KPI lookups.
    ContactStandardThe citizen. Name, email, phone, address. Vulnerability notes protected by column-level security.
    AccountStandardOrganisations: contractors, housing associations, or an advocate reporting for a resident.
    PropertyCustomUPRN, address, ward, tenure. Lets us see repeat repairs at one address.
    Notes and activitiesStandardNote (annotation) for free-text notes; activities (email, phone call, task) for dated contact. Both show on the case timeline.

    Relationships

    • Contact 1:N Case through the Customer lookup, which can also point to an Account. Account 1:N Contact.
    • Property 1:N Case, so repeat failures at one address are visible.
    • Case 1:N notes and activities, through Regarding. Case N:1 owner (user or team).

    Lifecycle mapping

    A Dataverse case has three statuses (Active, Resolved, Cancelled) with status reasons under each. The demo's New, Triage, In progress and Awaiting citizen would be status reasons under Active, with Awaiting citizen set as an on-hold reason that pauses the SLA. Resolving uses the standard Resolve Case action, which records the resolution, and reopening is Reactivate. The demo's separate team-leader "Closed" check has no direct standard equivalent, so that is a design decision to take with the architect.

    Business rules and logic

    • Damp and mould can't be logged below Urgent: a business rule with an error message, scoped to the table so it applies on the server as well as on the form.
    • Resolution note: captured by the standard Resolve Case dialog, not a custom rule.
    • Legacy reference is locked on the form by a business rule. Locking is a form-only action, so writes through the API or an import would need column-level security or a plugin.
    • Duplicate detection: a duplicate detection rule on active cases for the same property and category, which the user can review and override. The rule matches on Case columns, so the demo's postcode match would use the property lookup (to confirm).
    • SLAs: a Customer Service SLA with a "Resolve by" SLA KPI and an SLA item per priority, each with warning and failure times, business hours from a customer service schedule, and "Allow pause and resume" so on-hold status reasons stop the clock. No hand-built timers like this demo's.
    • Where logic lives: business rules for simple validation and form behaviour, Power Automate for notifications and anything that can run after the save, and plugins only where logic must run synchronously inside the save transaction.

    Security roles and team ownership

    RoleCase privileges (depth)
    CaseworkerCreate. Read at business-unit level. Write, append and assign at user level, so on their own cases. Access to cases their team owns would come through the security role given to that team. The aim is that they can pick up work from the team but not reassign a colleague's case. No delete. (Exact depths and team-role setup to prove with a test user per role.)
    Team leaderRead, write, assign and share at business-unit level. No delete.
    AuditorRead at organisation level, plus the privilege to view audit history. No create, write or delete.

    Housing Repairs would be its own business unit, so other council services don't see repairs cases by default. Cases start owned by an owner team per patch (North, South), with a queue for each, until a caseworker picks one up. Security roles are given to teams, not to individuals, so joiners and leavers are a group change. Auditing is on for Case and Contact. Nobody deletes cases by hand; they are resolved or cancelled.

    Environments and ALM

    1. Dev: unmanaged solution with our own publisher prefix; all changes made inside the solution.
    2. Test / UAT: managed solution, deployed by a pipeline. That is either Power Platform Pipelines (whose target environments must be Managed Environments) or Azure DevOps with the Power Platform Build Tools, whichever the programme uses.
    3. Production: managed only, with no direct edits. Solution checker runs before every release.
    4. Environment variables for API URLs and other per-environment settings, and connection references for flows, so nothing is re-pointed by hand after import.
    5. Every release versioned, with a release note. On my SharePoint project that meant 56 versioned app releases.

    Data protection (UK GDPR)

    • Case notes can hold health details, such as a child's asthma. That is special category data, so collect only what the repair needs and keep vulnerability notes behind column-level security.
    • Access is by role and audited, so the council can show who saw and changed a record.
    • Retention follows the council's schedule. Old cases are deleted or anonymised by a scheduled job under that schedule, not by users.
    • Dev and Test hold synthetic or masked data, never a copy of live.
    • The council, as data controller, is responsible for the impact assessment (DPIA) and takes its data protection officer's advice. My part is to supply accurate data flows and the role matrix.

    Integration: postcode and address lookup (REST)

    A custom connector over the council's address API (sketch below; the host is a placeholder). Custom connectors are described in OpenAPI 2.0 (Swagger), which is why the sketch isn't OpenAPI 3. A model-driven form can't call a connector on its own, so the lookup would run in a Power Automate flow when the case is saved, or in a custom page if staff need it as they type (to agree with the architect). The migration would call the same API to validate postcodes. Authentication would be OAuth 2.0 through Microsoft Entra ID, with the client secret held outside the solution, for example in Azure Key Vault. Custom connectors need premium licensing, which Dataverse and Dynamics 365 users normally already have. The form in section 1 simulates this call.

    swagger: "2.0"
info: { title: Address lookup (sketch), version: "0.1" }
host: api.example.org
basePath: /address/v1
schemes: [https]
produces: [application/json]
paths:
  /postcodes/{postcode}:
    get:
      operationId: LookupPostcode
      summary: Ward and addresses for a postcode
      parameters:
        - { name: postcode, in: path, required: true, type: string }
      responses:
        "200":
          description: Found
          schema:
            type: object
            properties:
              postcode: { type: string }
              ward:     { type: string }
              inArea:   { type: boolean }
              addresses:
                type: array
                items:
                  type: object
                  properties:
                    uprn:  { type: string }
                    line1: { type: string }
        "404": { description: Postcode not recognised }
